# 第3回 解答

## 演習

- 第1回（素のLLM）とエージェントの回答の違い：エージェントは用語集（search_glossary）を確認してから答え、「3レベル」を「基礎・実装・発展の3段階で、どれか1つに取り組めば完了」と講座の定義どおりに説明し、最後に関係する回（第1回）を示した。素のLLM（第1回の app.ask）は講座固有の用語集を参照できないため、講座で決めた意味を根拠を持って答えることができない
- `--trace` で見えたツール呼び出し（ツール名と引数）：「LoRAとQLoRAの違いは？」で `search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` の2回。docstring の「query には調べたい用語を1つだけ入れる」のとおり、用語を1つずつ検索した。2回実行して2回とも同じ呼ばれ方だった
- 1つの質問での LLM 呼び出し回数（`requests`）：2（tool_calls=2、input_tokens=1196）。1回目の呼び出しで2つの検索をまとめて指示し、ツールの結果を受け取った2回目の呼び出しで回答を作っていた。ツールを2回呼んでも LLM の呼び出しは2回だった
- 追加したツールと、docstring に書いた説明：`make_quiz(lecture: int)`。docstring は「指定した回（1始まりの整数）の用語から、確認問題を1問作って返す。『第2回の確認問題を出して』『第N回の内容でクイズを出して』のように、確認問題やクイズを求められたときに使う。返り値の question を出題し、answer を答え合わせに使う」。用語集から指定の回の用語を random.choice で1つ選び、`{"question": "「○○」の意味は？", "answer": 定義}` を返す。用語が無い回（lecture=0 など）には「第N回の用語は用語集にありません」と返すようにし、`uv run pytest -q` は 15 passed。「第2回の内容から確認問題を1問出して」で `make_quiz({'lecture': 2})` が呼ばれ（requests=2、tool_calls=1）、1回目は「ランク（LoRAのr）」、2回目は「量子化」と出題のたびに用語が変わった。モデルは answer を伏せて問題だけを出し、答えを考えるよう促した

## 宿題

- 取り組んだレベル：基礎
- やったこと：`app/tools.py` の `search_glossary` の docstring を1か所だけ変更し、`--list-tools` でモデルに渡る説明文が変わったことを確認してから、演習と同じ質問「LoRAとQLoRAの違いは？」を `--trace` 付きで3回実行して、変更前（2回）と比べた
  - 変更前：query には調べたい用語を1つだけ入れる（例: "LoRA"）。
  - 変更後：query には調べたい用語をまとめて入れる（例: "LoRA QLoRA"）。
- 結果：

  | 項目 | 変更前（1つだけ） | 変更後（まとめて） |
  |---|---|---|
  | ツール呼び出し | `search_glossary('LoRA')`、`search_glossary('QLoRA')` | `search_glossary('LoRA QLoRA')` |
  | tool_calls | 2（2回とも） | 1（3回とも） |
  | requests | 2（2回とも） | 2（3回とも） |
  | input_tokens | 1196 | 1111（約7%減） |
  | output_tokens | 196 / 222 | 260 / 211 / 210 |
  | 回答 | LoRA・QLoRA の定義を説明し「関係する回：第2回」 | 同じく両方を説明し第2回を示した。内容の正しさは変わらなかった |

  - docstring の1文を変えただけで、モデルが渡す引数とツールの呼び出し回数が変わった。モデルは docstring の例（"LoRA QLoRA"）の形をそのまま真似していた
  - requests は変わらなかった。変更前も2つの検索を1回目の LLM 呼び出しでまとめて指示していたため、検索回数が減っても LLM の呼び出し回数は減らない。減ったのはツールの結果としてモデルに渡す文字量（input_tokens）だった
  - 回答の中身はほぼ同じだったが、変更後の1回目には「本講座の演習でもLoRAが使われます」「発展課題として比較することがある」など、用語集の説明に寄った補足が増えた
  - 検索関数を手元で直接呼んで確かめると、`search_glossary("LoRA QLoRA")` は LoRA と QLoRA の2件を返していた。検索は空白を取り除いて部分一致で探すため、まとめて入れても今回はたまたま両方見つかった。一方、変更前の `search_glossary("LoRA")` だけでも LoRA・ランク（LoRAのr）・QLoRA の3件が返っており、変更前の2回目の検索は結果が重なっていた
- 気づき・疑問：
  - docstring はコメントではなく、モデルへの指示として効く。1文の書き方（特に例）で、ツールの使われ方が変わる
  - 「まとめて入れる」が良いかどうかは、ツールの実装しだいである。`search_glossary` は最大3件（MAX_RESULTS=3）しか返さないため、手元で `"LoRA QLoRA PEFT 量子化"` を検索すると PEFT・LoRA・QLoRA の3件だけになり、量子化が落ちた。用語が多い質問では、まとめて検索すると取りこぼしが起き、エージェントは気づかずに答える可能性がある
  - そのため、docstring は「モデルに何をさせたいか」だけでなく、「ツールが実際にどう動くか（何件返すか、どう一致させるか）」と合わせて書く必要があると感じた。今回の用語集検索では、元の「1つだけ入れる」のほうが安全だと考える
  - 疑問：ツール呼び出しを減らしたいとき、docstring で引数の形を変えるのと、ツール側で複数の語を受け取れるようにする（例：`queries: list[str]`）のと、どちらが安定するか
